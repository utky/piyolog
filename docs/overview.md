# ぴよログ → BigQuery データ基盤: 全体設計ドキュメント

## 0. このドキュメントの位置づけ

ぴよログ(育児記録アプリ)のエクスポートデータを Google Cloud (BigQuery) に永続化し、種別ごとの分析を可能にするデータ基盤の**全体設計**を記す。

raw層に限定した実装指示は別ドキュメント(`piyolog_raw_layer_spec.md`)を参照。本ドキュメントは raw から marts までのレイヤー全体像と、各層の設計方針・確定した判断・その根拠を俯瞰するためのもの。

実装の進め方は段階的: **まず raw層を実装して動かし**、種別の棚卸しや staging 以降の構造化は BQ に入った生データへの探索クエリを通じて反復的に詰める。本ドキュメントの staging 以降は「確定した方針」と「未確定の検討事項」を区別して記載する。

---

## 1. 目的とスコープ

### 達成したいこと

- ぴよログの育児記録を構造化データとして BigQuery に永続化する。
- **特定のイベント種別だけを取り出した集計**(例: 睡眠時間の推移、体温の記録、授乳量の変化、マイオブレースの実施率)を直接 SQL で書けるようにする。
- 日次の自由記述メモを全文検索できるようにする。
- 子供が複数いるため、子供ごとのデータを区別して扱えるようにする。

### このプロジェクトの性質

- 個人の家庭内データ基盤。データ量は小さい(数年分でも数MB規模)。
- 取り込みは低頻度(月次程度)、リアルタイム性は不要。
- 反復的な改善を前提とする。完璧な初期設計より、動かしながら育てることを優先。

## 2. 制約条件(設計の前提)

| 制約 | 内容 | 設計への影響 |
|---|---|---|
| API なし | ぴよログには API がなく、データ取得はスマホアプリの月次テキストエクスポートのみ | データ取得部分は人間の操作(エクスポート)を介さざるを得ない |
| 子供ごとに別ファイル | 1ファイル内は1人の子供の記録のみ | 照合キーから child_name を外せる(後述) |
| ファイル名に名前なし | `【ぴよログ】YYYY年M月.txt` 形式。子供名を含まない | 子供の区別は Drive のフォルダ構成で行う |
| 発達段階で種別が激変 | 乳児と幼児で記録種別が大きく異なる | 既知種別リストは全期間・全子供の和集合で定義する必要 |
| 集計項目が可変 | 月によって集計ブロックの項目が増減(例: 搾母乳合計) | 集計ブロックを「マーカーで挟まれた可変領域」として扱う |
| パースの状態依存性 | 詳細テキストが複数行に渡り、逐次処理が必要 | BQ(SQL)完結は困難。手続き的処理(Python)が必要 |

## 3. 全体アーキテクチャ

### データフロー

```
[スマホ] ぴよログ月次エクスポート
   │  共有メニュー → Google Drive の子供別フォルダへ保存
   ▼
[Google Drive] ぴよログ/<child_name>/【ぴよログ】YYYY年M月.txt
   │  Drive API で直接読み取り(GCSは経由しない)
   ▼
[Cloud Run job] (Python, バッチ, 手動 or スケジュール起動)
   │  ファイル列挙 → 本文取得 → ファイル単位で洗い替えロード
   ▼
[BigQuery: raw]   テキスト全文を1ファイル1レコードで保持
   │  ▲ パースロジック改善時はここから再パース(Drive再アクセス不要)
   │  dbt
   ▼
[BigQuery: staging]  行レベルにパースした生レコード(正規化)
   │  dbt
   ▼
[BigQuery: intermediate]  種別ごとテーブル / 区間データ / enrich
   │  dbt
   ▼
[BigQuery: marts]  利用アプリケーション特化のデータマート
```

### データ取得部分とデータ処理部分の分離

パイプラインは2つの部分に分かれる。

- **データ取得部分**(人間の操作を含む): スマホでエクスポート → Drive へ共有保存。ここは完全自動化が困難。
- **データ処理部分**(完全自動化可能): Drive → BQ → dbt 変換。

データ取得部分の摩擦を最小化するため、スマホ側操作を「共有 → Drive」だけで完結させ、それ以降をサーバー側に寄せている。

## 5. レイヤー構成(dbt)

dbt のレイヤリング慣習に沿う。staging はソースに対する薄い変換、intermediate は結合・分割のロジック、marts は用途特化。

### 5.1 raw

- テキスト全文を保持。詳細は `piyolog_raw_layer_spec.md`。
- スキーマ: `child_name`, `source_year_month`(DATE, 月初日), `file_name`, `drive_file_id`, `raw_content`, `loaded_at`。
- 洗い替え単位: `(child_name, source_year_month)`。

### 5.2 staging(行レベル, 正規化) ※方針確定・実装は今後

raw の `raw_content` を状態機械でパースし、出現単位に応じてテーブルを分離する。**なるべく生データを残す**。

| テーブル | 粒度 | 主なカラム |
|---|---|---|
| `stg_daily_header` | 日次1レコード | source_year_month, log_date, child_name, child_age_raw |
| `stg_events` | イベント1レコード | source_year_month, log_date, event_seq, event_time, event_type_raw, detail_raw |
| `stg_daily_notes` | 日次1レコード | source_year_month, log_date, note_raw |

- 照合キー: `(source_year_month, log_date)`。1ファイル=1子供のため child_name はキーに不要。
- child_name / 年齢はファイル・日次に1回しか出ないので、イベント行ごとには持たせない(正規化)。必要時はヘッダーと結合。

#### パース状態機械(確定仕様)

各日次セクション(`----------` 区切り)を上から走査し、4状態を遷移する。

1. **HEADER**: 日付行 `YYYY/M/D(曜)` と 名前・年齢行 `名前 (X歳Yか月Z日)` を読む。
2. **EVENTS**: `母乳合計` 行に到達するまで。
   - イベント開始行判定: 行頭 `^\d{1,2}:\d{2}\t`(時刻の直後がタブ)。
   - 合致しない非空行は直前イベントの `detail_raw` に改行付きで追記。
3. **SUMMARY**: `母乳合計` 行〜`うんち合計` 行。間の項目数は可変(`搾母乳合計` 等が入りうる)。BQには保持せず読み飛ばす。
4. **NOTES**: `うんち合計` 行の次行〜セクション末尾。全文を `note_raw` として収集(`【見出し】` 含む)。

### 5.3 intermediate(種別ごと + 区間) ※一部方針確定・設計は今後

#### 種別ごとテーブル(タイプ別)

`stg_events` を既知種別ごとに分割。各種別固有スキーマで `detail_raw` を構造化する。

確認済みの種別グループ(幼児1名, 乳児1名の2ファイルから観察):

- **数値/量型**: 体温(数値+単位), のみもの(ml), ミルク(ml), 搾乳/搾母乳(ml)
- **状態型**: 起きる(継続時間付き), 寝る, おしっこ, うんち(量補足: 多め/少なめ/ちょこっと/やわらかめ/色)
- **授乳型**: 母乳(左右の分数 + 授乳順記号 ▶◀ + 補足)。フォーマット複数あり(`左20分 ▶ 右20分` / `左15分 / 右18分` / `右6分` / 時間情報なし)
- **自由記述型**: 離乳食, ごはん, おやつ, さんぽ, 行き先イベント, 病院, 幼稚園, その他
- **トレーニング型**: マイオブレース(達成記号 🔴△❌)
- **ルーティン型**: 生活習慣, スキンケア, くすり, ミルトン交換
- **発達記録型**: できた(寝返り, ズリバイ 等)

※ 上記は2ファイルからの暫定。**全期間の棚卸し(後述TODO)で和集合を確定する**。

#### 区間データ

- `sleep_intervals`: `寝る` → `起きる` のペアリングで睡眠区間を構築。`起きる` に付随する継続時間を信頼して duration とする(方針Y)。staging では生のまま(方針X)、区間化は intermediate で行う。
- 必要に応じて enrich(年齢の構造化、曜日・時間帯の付与 等)。

### 5.4 marts ※用途が固まってから

利用アプリケーション特化のデータマート。用途候補: 月次レポート生成、健康記録ダッシュボード、Obsidian への日次ノート連携 等。

## 6. 横断的な設計事項

### 6.1 冪等性 / 洗い替え

- 洗い替え単位は `(child_name, source_year_month)`。月次ファイルの再エクスポート・訂正に対応。
- job 再実行が安全(結果が壊れない)であること。

### 6.2 未知種別の扱い(方針P)

- 既知種別を固定的に定義し、パース時に未知種別が出たら**警告/エラーで検知**する。
- パース処理が品質ゲートを兼ねる。アプリ更新で記録項目が増えた場合に気づける。

### 6.3 全文検索(daily_notes)

- シンプル方針: `SEARCH` 関数 または `REGEXP_CONTAINS`。
- データ量が小さい(数年分で数百〜数千行)ため、専用 SEARCH INDEX は当面不要。
- 将来、病院記録やイベント詳細も含めた横断検索が必要になれば INDEX 方針を再検討。
