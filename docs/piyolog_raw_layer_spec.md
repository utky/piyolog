# ぴよログ → BigQuery 取り込み: raw層 実装指示書

## 0. このドキュメントの位置づけ

ぴよログ(育児記録アプリ)のエクスポートデータを Google Cloud (BigQuery) に永続化するプロジェクトの、**raw層に限定した実装指示書**である。

raw層より先(staging以降の構造化)は本ドキュメントの「TODO(raw層完成後に検討)」に列挙するのみで、**今回の実装スコープには含めない**。まず raw層を動かし、その後の設計は BQ に入った生データに対する探索クエリを通じて反復的に詰める方針。

---

## 1. 背景と制約

- ぴよログには API がない。データ取得は**スマホアプリからの月次テキストエクスポートが唯一の経路**。
- エクスポートは**子供ごとに別ファイル**。1ファイル内には1人の子供の記録のみ。
- ファイル名は既定で `【ぴよログ】YYYY年M月.txt` 形式(例: `【ぴよログ】2024年10月.txt`)。**ファイル名に子供の名前は含まれない**。
- エクスポートファイルは Google Drive 上の**子供別サブフォルダ**に置く運用とする(例: `ぴよログ/child_a/`, `ぴよログ/child_b/`)。
- 取り込みにリアルタイム性は不要。**まとめてバッチ処理**でよい。

---

## 2. 全体アーキテクチャ(確定事項)

```
[スマホ] ぴよログ月次エクスポート
   │  共有メニュー → Google Drive の子供別フォルダへ保存
   ▼
[Google Drive] ぴよログ/<child_name>/【ぴよログ】YYYY年M月.txt
   │  Drive API で直接読み取り(GCSは経由しない)
   ▼
[Cloud Run job] (Python, バッチ, 手動 or スケジュール起動)
   │  ファイル列挙 → 本文取得 → ファイル単位で洗い替えロード
   ▼
[BigQuery] raw テーブル(1ファイル1レコード, テキスト全文を保持)
   │
   ▼
（以降 staging / intermediate / marts は dbt で。今回スコープ外）
```

### 設計判断の要点(なぜこうするか)

- **GCSを経由せず Drive API で直接読む**: スマホ側の操作を「共有 → Drive」だけで完結させ、日常運用の摩擦を最小化するため。Drive→GCS同期という余計な一段を排除する。代償としてjob側にDrive API読み取りの実装が必要だが、これは一度きりのサーバー側実装。
- **raw層にテキスト全文をBQへ保持する(b案)**: パースロジックを後から修正・改善した際、Driveに再アクセスせず BQ内で何度でも再パースできるようにするため。raw を source of truth のコピーとして持つ。
- **Cloud Run jobs を採用(functions ではなく)**: リアルタイム性が不要で、複数ファイルをまとめてプル型で処理したいため。イベント駆動(functions)ではなく、起動時にフォルダをスキャンする方式が運用イメージに合う。
- **コストは事実上ゼロ想定**: 月数回・数十KB・数秒の処理。Cloud Run jobs/functions いずれも「実行時間ぶんだけ課金、アイドルは無料」で、本ワークロード規模では課金は問題にならない。

## 3. raw テーブル スキーマ(確定)

データセット名・テーブル名は実装者裁量(例: `piyolog_raw.daily_export_files`)。カラムは以下で確定。

| カラム名 | 型 | 説明 |
|---|---|---|
| `child_name` | STRING | 子供の名前。**Driveのサブフォルダ名から付与**(本文パースには依存しない)。例: `child_a`, `child_b` |
| `source_year_month` | DATE | データの対象年月。**月初日**で表現(例: 2024年10月 → `2024-10-01`)。ファイル名から抽出 |
| `file_name` | STRING | 元のファイル名(例: `【ぴよログ】2024年10月.txt`) |
| `drive_file_id` | STRING | Drive のファイルID。再取得・追跡用 |
| `raw_content` | STRING | テキストファイルの全文 |
| `loaded_at` | TIMESTAMP | この取り込み処理を実行した時刻(UTC) |

### キー設計

- **洗い替えの単位キー = `(child_name, source_year_month)`**。
- 同一年月でも子供が異なれば別レコードとして共存する。
- 月次ファイルの再エクスポート・訂正に対応するため、取り込み時は**同一 `(child_name, source_year_month)` の既存レコードを削除してから挿入**(ファイル単位の洗い替え)。

### `source_year_month` を DATE(月初日)にした理由

洗い替えキーであると同時に「いつのデータか」の時間軸絞り込みにも使う。DATE型なら範囲指定(`WHERE source_year_month >= '2024-01-01'`)や `EXTRACT(YEAR ...)` 等がそのまま使え、後段の期間集計と整合する。月次データを月初日のDATEで持つのは一般的な慣行。

## 4. Cloud Run job の処理仕様

### 言語・ライブラリ

- **Python**(BQ/dbtエコシステムとの親和性のため)。
- Google Cloud クライアントライブラリ(`google-cloud-bigquery`)、Drive API クライアント(`google-api-python-client` 等)。

### 処理フロー

1. **対象フォルダの決定**
   - 子供別サブフォルダを処理対象とする。`child_name` とフォルダIDの対応を設定(環境変数・設定ファイル・引数いずれか。実装者裁量)。
   - 参考: 現状 Drive 上では、ファイルはフォルダ `1BDMCTkCaFEbskGeIGKDzWuUdsb86ME7R` に直接入っている(子供別サブフォルダは未整備)。**運用開始前に、ユーザーがファイルを子供別サブフォルダへ整理する前提**。実装は「child_name → フォルダID のマップを受け取り、各フォルダを処理する」汎用形にしておくこと。

2. **ファイル列挙**
   - 各対象フォルダ内の `mimeType = 'text/plain'` かつ タイトルが `【ぴよログ】` で始まるファイルを列挙。
   - Drive API のページネーション(`nextPageToken`)に対応すること。フォルダあたり数十ファイル規模になりうる。

3. **本文取得**
   - 各ファイルの本文(プレーンテキスト)を取得する。
   - 文字コードは UTF-8 想定。絵文字(🔴 等)や全角記号(▶ ◀ / など)を含むため、エンコーディングを壊さないこと。

4. **メタデータ抽出**
   - `file_name` からタイトルの `YYYY年M月` を正規表現で抽出し、`source_year_month` を月初日の DATE に変換(例: `2024年10月` → `2024-10-01`)。
   - `child_name` は処理中のフォルダに対応する名前を付与。
   - `drive_file_id` は Drive のファイルIDを格納。
   - `loaded_at` は処理実行時刻(UTC)。

5. **BQへロード(ファイル単位の洗い替え)**
   - 各ファイルについて、`(child_name, source_year_month)` が一致する既存レコードを削除 → 当該ファイルのレコードを挿入。
   - 全ファイル処理を1回のjob実行でまとめて行う。

### 冪等性

- 同じファイルを再取り込みしても重複しないこと(洗い替えにより保証)。
- job の再実行が安全(at-least-once 実行で結果が壊れない)であること。

### 起動方法

- 手動起動を基本とし、必要に応じて Cloud Scheduler で定期化できる構成にしておく(常駐サービスにはしない)。

## 5. 入力データの構造(raw層では解釈しないが、参考情報)

raw層は**本文を解釈せずそのまま格納する**ため、以下は実装に必須ではない。ただしファイル名抽出のテスト用、及び後続フェーズの理解のために記す。

### ファイル全体構造

```
【ぴよログ】2026年5月          ← ファイル先頭行(対象年月)
----------                      ← 日次セクション区切り
2026/5/1(金)                    ← 日付行
child_a (4歳4か月20日)           ← 名前・年齢行
（空行）
HH:MM<TAB>種別<TAB>詳細          ← イベント行(詳細は複数行に渡ることがある)
...
母乳合計 ...                     ← 集計ブロック開始
ミルク合計 ...
（搾母乳合計 ... など可変項目が入りうる）
睡眠合計 ...
おしっこ合計 ...
うんち合計 ...                   ← 集計ブロック終了マーカー
（空行）
自由記述メモ(【見出し】を含むことがある)
----------                      ← 次の日次セクション
...
```

### 注意点(後続フェーズで効く既知の観察事実)

- 子供の発達段階で種別が大きく異なる(乳児: 母乳/ミルク/ミルトン交換/搾乳/搾母乳/できた、幼児: マイオブレース/幼稚園 等)。
- 集計ブロックの項目数は固定ではない(例: `搾母乳合計` が入る月がある)。`母乳合計`〜`うんち合計` で挟まれた可変ブロックとして扱う。
- 同一種別でも詳細フォーマットに複数バリエーションがある(例: 母乳 `左20分 ▶ 右20分` / `左15分 / 右18分` / `右6分` / 時間情報なし)。
- 絵文字・全角記号が頻出。文字化けに注意。

## 6. TODO(raw層完成後に検討。今回スコープ外)

raw層が BQ で動いた後、以下を BQ 上の `raw_content` に対する探索クエリ/dbt を通じて反復的に設計・実装する。

1. **種別の棚卸し**: 全期間の `raw_content` から `時刻+TAB+種別` を機械抽出してユニーク化し、既知種別リストを確定する(方針P=既知種別を固定定義し未知種別は警告で検知 + 方針ii=全期間棚卸し)。child_a の過去分は 2021年12月〜 が Drive に存在する。
2. **行レベル staging のパース実装**: 状態機械(HEADER → EVENTS → SUMMARY → NOTES)。
   - イベント開始行判定: 行頭 `^\d{1,2}:\d{2}\s+`(時刻直後は半角スペース区切り。基本3スペース、まれに1スペースの例外あり。タブは実データに存在しない)。これに合致しない非空行は直前イベントの詳細へ追記。
   - EVENTS終了マーカー: `母乳合計` で始まる行。
   - SUMMARY範囲: `母乳合計` 行〜`うんち合計` 行(間の項目数は可変)。集計値はBQに保持しない(都度集計方針)。
   - NOTES範囲: `うんち合計` 行の次行〜セクション末尾。
   - パースは BQ完結が困難(状態を持つ逐次処理が必要)なため、Cloud Run job / dbt Pythonモデル等の手続き的処理で行う。
3. **staging のテーブル分割(正規化)**: 出現単位に応じて分離。
   - `stg_daily_header`(日次1レコード: child_name, child_age_raw, log_date 等)
   - `stg_events`(イベント1レコード: event_time, event_type_raw, detail_raw, event_seq 等)。`(source_year_month, log_date)` でヘッダーと結合。
   - `stg_daily_notes`(日次1レコード: note_raw)
   - staging方針: なるべく生データを残す。child_name/年齢はファイル/日次に1回しか出ないのでイベント行ごとには持たせない。
4. **種別ごと intermediate(タイプ別テーブル)**: 約19種類+乳児系。各種別固有スキーマで詳細を構造化(体温→数値、のみもの/ミルク→ml、おしっこ/うんち→量補足、母乳→左右時間+授乳順記号、マイオブレース→達成記号 等)。特定イベントだけの集計を直接SQLで書けるようにするのが目的。
5. **区間データ intermediate**: `sleep_intervals`(寝る→起きるのペアリング。`起きる` に付随する継続時間を信頼して duration とする)等。必要に応じて enrich。
6. **daily_notes 全文検索**: シンプル方針(`SEARCH` 関数 または `REGEXP_CONTAINS`)。専用 SEARCH INDEX は当面不要。
7. **marts**: 利用アプリケーション特化のデータマート。
8. **dbt プロジェクト構成**: モデル配置・命名・テスト。staging(行レベル) → intermediate(種別ごと/区間) → marts のレイヤリング。
